- [ ]  pith 3.5h — ① UART RX + 링버퍼
    - 공부할 것: USART RXNE 인터럽트, ORE(오버런) 플래그와 SR → DR 읽기로 지우는 순서, 링버퍼 head·tail, 한 칸 비워서 full과 empty 구분하기, 크기를 2의 거듭제곱으로 두고 마스킹
    - 개인 공부
        
        개인적으로 Watch dog 시스템을 추가하고 싶어서 먼저 구현한다.
        
        ---
        
        Watch dog은 SW가 정상적인 흐름을 벗어났을 경우 이를 감지하고, MCU를 다시 시작하는 안정 장치이다. 이는 임베디드 시스템에서 현장 복구성을 높이는 기본 장치중 하나이다.
        
        Watch dog 시스템에는 WWDG왜 IWDG가 존재한다.
        
        - WWDG (Window Watchdog): 설정된 시간 윈도우보다 너무 빠르거나 늦게 카운터를 리프레시하면 MCU를 Reset한다.
            - 클럭 기준: APB 클럭을 기반으로 카운터를 동작시킨다. (WWDG도 주변 장치이기 때문이다.)
                - APB Clock : APB 버스에 연결된 주변장치들이 동작할 타이밍을 제공한다.
                - APB 클럭에 내부 고정 분주값 `4096`과 설정 가능한 Prescaler를 적용하여 카운터 클럭을 생성한다.
                - 카운터 클럭 주파수: `PCLK / (4096 × Prescaler)`
                - 예를 들어 APB 클럭이 36MHz이고 Prescaler가 1이라면, 카운터 클럭은 약 8,789Hz이다. 즉, 카운터가 약 114μs마다 1씩 감소한다.
            - **Window**: 카운터 값이 설정된 윈도우 범위에 들어왔을 때만 정상적으로 리프레시할 수 있다. 허용 범위보다 일찍 리프레시하거나 제한 시간 내에 리프레시하지 못하면 Reset이 발생한다.
        - IWDG (Independent Watchdog) : 정해진 시간 안에 타이머를 초기화 해야한다.
            - 이는 정해진 시간 안에 어떻게든 refresh를 진행할 시 비정상 처리로 인식하지 않는다.
            - 차이점은 WWDG와는 달리 LSI 클럭을 사용한다는 점이다.
                - Low-Speed Internal oscillator (LSI) : MCU내부 저속 발진기
                    - System clock/APB clock은 이상이 생길 시 시스템 전체에 영향을 줄 수 있다. 하지만 LSI같은 단독 클럭을 사용할 시 독립적으로 동작하기 때문에 시스템 문제에 영향을 받지 않고 계속 Watch Dog을 진행할 수 있다.
                        - 독립적인 WatchDog이 목표인 IWDG에 적합한 클럭이다.
                    - 내부에서 저전력으로 동작하기 때문에 별도 부품이 필요하지 않지만, 주파수가 정확하지 않을 수 있다.
        
        Early Wakeup Interrupt (EWI) : WWDG, IWDG가 임계에 도달하여 Reset을 발생시키기 전에 마지막으로 만들 수 이는 인터럽트이다.
        
        - IWDG의 EWI를 지원하지 않는 모델이 있을 수 있다.
        
        각각의 WatchDog 선택 조건은 다음과 같다.
        
        WWDG만으로 충분할 수 있는 경우
        
        - 메인 루프나 주기적 태스크가 정상적으로 실행되는지 확인하려는 목적
        - 갱신 주기가 정해져 있고, 너무 빠르거나 느린 실행을 감지하고 싶은 경우
        - 시스템 클럭 장애까지 별도로 대비할 필요가 크지 않은 경우
        
        IWDG를 선택할 근거가 있는 경우
        
        - 시스템 클럭 설정이나 클럭 소스에 문제가 생겨도 워치독이 계속 동작해야 하는 경우
        - WWDG의 APB 클럭 의존성 때문에 감시 기능까지 영향을 받을 가능성을 줄이고 싶은 경우
        - 독립적인 타임아웃 기반 복구를 요구사항으로 명시한 경우
        
        PITH프로젝트에서는 직접 구현한 기능들의 독립적인 WatchDog을 하기 위해서 IWDG를 구현할 계획이다.
        추가로 Main Loop 검사를 위해서 전체 클럭 검사 WWDG역시 도입할 계획이다.
        
    - 확인 질문: 링버퍼가 가득 찼는지 비었는지 head·tail만으로 어떻게 구분하나?
- [x]  CS 1h — [C] volatile · static · const · extern
    - 소주제: 컴파일러 최적화와 volatile, ISR 공유 변수·레지스터, static의 세 가지 쓰임, const 포인터 구분
        - Study
            
            컴파일을 실행할때 컴파일러는 코드가 바꾸지 않는 변수의 값은 그대로라고 가정하고, 읽기/쓰기 횟수를 감소시켜 비용을 절약한다.
            
            ```c
            for (i = 0; i < 100000; i++) {}
            ```
            
            다음과 같은 코드에서 컴파일러는 for문이 아무것도 실행하지 않기 때문에, 이를 제거한다. 이 역시 컴파일러 최적화이다.
            디버깅 모드에서는 정상적으로 동작하지만, 실제 빌드 시 오류가 발생한다면 보통 이러한 이유이다.
            
            그렇기 때문에 컴파일러에게 특정 변수에 대해 최적화를 진행하지 않도록 키워드를 사용해 주어야 한다. 
            
            - volatile : 소스에 사용한 횟수만큼 무조건 메모리에 쓰고, 다시 읽는다.
                - 하지만 volatile이 Atomic한 연산까지 지원하진 않고, 동기화 문제 해결 요소로도 사용할 수 없다. 또한 컴파일러 문제만 해결하기 때문에 하드웨어적으로 발생하는 문제를 해결할 수 없다. 또한 계속 읽고, 쓰기 때문에 비용이 발생한다.
                - 이는 컴파일러 코드 밖에서 시도하는 값 변경에 필수적이다. HW가 호출하는 ISR이 루틴에 따라 변경한 값을 변경하여도, 다른 곳에서 새로운 값을 읽지 않으면 문제가 발생하기 때문에 volatile을 사용한다.
            
            레지스터 역시 하드웨어가 값을 바꾸고, 읽기·쓰기 자체가 동작이라서 volatile이 필수이다.
            
            ISR은 Interrupt를 처리하는 루틴으로, main 중간에 호출될 수 있다. ISR이 main 중간에 끼어들어 main이 사용하던 값을 변경할 시 ISR을 종료시키지 못하는 main은 이를 제지할 수 없다. 그렇기 때문에 다음 세 설계를 적용해야한다.
            
            1. ISR은 쓰기만 진행, main은 읽기만 진행
            2. 함께 사용하는 데이터는 묶어서 원자적으로 읽을 수 있게 한다. 
            3. ISR은 짧게 진행하여 Flag에 기록과 최소한의 처리만 가능하게 하고, main에서 긴 분기를 처리한다.
                - 긴 계산에서 다음 UART의 신호가 밀릴 수 있다. (Overrun)
                - 다른 Interrupt가 밀린다.
        - Study2
            
            static 키워드는 세 가지 역할을 한다.
            
            1. 지역 변수 → 저장 기간 변경 (함수가 끝나도 .data/.bss에 는다)
            2. 전역 변수 → 링키지 변경 (다른 파일에서 extern으로 못 가져간다)
            3. 함수 → 링키지 변경 (다른 파일에서 호출 못 한다)
                - 컴파일 과정은 다음과 같이 진행된다.
                    - 전처리 (.i) → 컴파일 (.s) → 어셈블리 (.o) - > 링커 (.elf)
                    - 같은 이름을 링커가 다른 파일과 이어 줄 수 있는지 나타낸다.
                    - 심볼이 global에서 local로 바뀌어(nm에서 T→t, B→b) 링커가 다른 파일과 연결하지 않는다.
                        - 이로 인해 다른 파일 접근 불가 등을 지정할 수 있다.
                        - 심볼이 바뀌므로 링커가 외부 링키지를 할 수 없다.
            
        - Study3
            
            Const는 해당 변수/함수 이름으로 값을 변경하는 것을 막는다. 기본적으로 const를 기준으로 왼쪽을 고정하고, 왼쪽이 비었다면 오른쪽 내용을 고정한다.
            
            ```c
            const int *a         // 값 변경 불가/주소 변경 가능
            int * const a       // 값 변경 가능/주소 변경 불가
            const int * const a // 값 변경 불가/주소 변경 불가
            ```
            
            위 코드는 2번 명령줄은 값은 RAM에 위치하고, 어떤 주소는 Flash에 위치할 것이고, 또 1번 줄은 반대이다. 3번은 명령줄 전부 Flash에 위치한다.
            
            const가 아닌 데이터에 const를 추가하는 것은 문제가 없다. 
            
            - `int *` 를 `const int *` 로 바꾸는 비용이 없다.
            
            하지만 const 데이터에서 const를 지우기 위해서는 타입 캐스팅을 해야한다.
            
            const는 값이 바뀌지 않으므로 Flash 메모리에 들어갈 것이다. (Code 메모리 영역) , 하지만 const가 없다면, 값이 바뀔 수 있으므로 RAM에 위치시켜야한다. 
            
    - 대표 질문: volatile은 언제, 왜 쓰나?
        - Answer
            
            컴파일러는 최적화할 때, 지금 컴파일하는 코드 줄에서 바꾸지 않는 변수의 값은 그대로라고 생각한다. 그래서 값을 레지스터에 두고 재사용하거나, 필요 없어 보이는 읽기와 쓰기를 생략한다.
            
            문제는 ISR이나 하드웨어처럼 코드 흐름 밖에서 값이 바뀌는 경우이다. 예를 들어 SysTick ISR이 올리는 tick 변수를 main에서 기다리면, main은 처음 읽은 값만 보고 무한 루프에 빠질 수 있다. volatile은 그 변수의 모든 읽기와 쓰기를 실제 메모리 접근으로 하게 만들어 이 문제를 막는다. 그래서 ISR과 공유하는 변수, 그리고 하드웨어가 값을 바꾸는 메모리 맵 레지스터에 volatile을 사용한다.
            
            다만 volatile은 컴파일러 최적화만 막을 뿐, 원자성이나 동기화는 보장하지 않습니다. 그래서 두개 이상의 task가 접근하여 값을 수정하는 변수는 임계 구역이나 atomic으로 따로 보호해야 한다. 또 매번 메모리에 접근하는 비용이 있어서 꼭 필요한 변수에만 붙인다.
            
    - 복습: 메모리 영역 대표 질문에 1분 안에 답하기
        - Answer
            
            메모리 영역은 프로그램이 실행되며 사용하는 명령어와 데이터를 저장하는 곳이다. 메모리 영역을 나누는 이유는 데이터마다 수명과 특성이 다르기 때문이다. 메모리 영역은 코드, 데이터, 힙, 스택으로 이뤄진다. 코드에는 Read-only로 실행 명령어 (코드)가 저장되며, 삭제되지 않는다.  데이터에는 정적 변수와 전역 변수가 저장된다. bssd에 초기화되지 않은 값과 0으로 초기화된 값이 저장되며, data 섹션에는 초기 값이 잆는 전역/정적 변수가 저장된다. 힙은 개발자가 직접 할당받을 수 있는 메모리 영역이다. 이는 개발자가 할당 후 해제까지 관리한다. 프로그램 실행 중에 동적으로 할당 가능하다. 스택은 지역 변수/함수 호출 등이 저장되며 함수가 종료되면 메모리가 해제된다.
