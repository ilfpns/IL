- [ ]  CS 1h — [OS] 동기화: 뮤텍스 vs 세마포어
    - 소주제: 경쟁 상태, 임계 구역, 뮤텍스(소유권), 이진/카운팅 세마포어, 스핀락
    - 대표 질문: 뮤텍스와 세마포어의 차이는?
        - Study
            - 경쟁 상태 (Race condition)
                - 진입 시점이나 타이밍에 따라 결과가 달라지는 상황을 의미한다. 만약 공유 자원을 사용한다고 할 경우 서로 타이밍이 안 맞게 접근하면, 데이터 동기화 문제가 발생할 수 있다. 비슷한 시점에 값을 읽고 서로 다른 쓰기 연산을 수행하여, 쓰기 연산이 꼬이는 것이다. 이때 공유 자원에 접근하며 명령을 수행하는 코드 부분은 임계 영역 (Critical Section)이다. 
                
                동기화 알고리즘은 다음 세 조건을 만족해야한다.
                    - Mutual Exclusion : 상호 배제 ⇒ 한번에 하나의 Task만 임계 영역 진입 가능
                    - Progress : 진행 ⇒ 임계 영역을 사용하는 Task가 없다면, 기다리는 Task는 진입해야함
                    - Waiting bounded : 한정 대기 ⇒ 자원을 기다리는 Task는 무한히 기다리면 안 됨
            - 스핀락 (Spin-lock)
                - OS가 지원하는 동기화 알고리즘이다.
                - 정수형 변수로 이뤄지며, P, V 연산만을 통해 접근할 수 있다.
                    - P, V 연산은 모두 OS가 atomic한 연산을 지원한다.
                    - P (atomic한 연산)
                        - 자원을 사용하는 함수
                    - S (atomic한 연산)
                        - 자원을 반납하는 함수
                - P, V 연산을 OS가 atomic하게 지원하여, 간단하게 동기화 조건 2개를 만족한다. (상호 배제, 진행) 하지만 첫 Task종료 이후 Task2가 마지막 while을 마치기 전에 Task3이 진입하면 Task2는 먼저 자원을 기다리고 있었음에도 자원을 사용하지 못하고 밀림, 이런 현상이 우연으로 계속 반복되면 Task2는 계속 자원을 기다리며 한정 대기 문제에 걸린다.
                Task2는 계속해서 while을 반복하며, 특별히 연산 명령을 진행하지 않고, 값의 변경만 확인하며 loop에서 계속해서 CPU자원을 사용하는 것을 busy waiting 이라고 한다.
                - 또한 Spinlock은 실행 환경에 영향을 받는다. 만약 실행 환경이 단일 프로세서 환경이라면 Spinlock을 사용하는 것이 오히려 문제가 될 수 있다. 먼저 P연산을 통해 CS (Critical Section)에 진입하고, 다음 Task는 P를 실행해서 계속 사용 가능한 자원을 점검하며 busy waiting 돌 것이다. 이때 기존에 P로 CS에 들어간 Task의 작업을 돌며, 기다리는 Task의 P연산도 loop해주어야 하니, 두 일을 동시에 처리하며, 오히려 먼저 들어간 Task가 제 시간에 끝나지 못하는 비효율적인 상황이 발생할 수 있다.
                    
                    그렇기 때문에 각자 독립적으로 명령을 수행할 수 있는 멀티 프로세서 환경에서 Spinlock이 유용하다. 먼저 Lock을 획득한 Task는 Critical Section의 명령을 수행하고, Lock을 획득하지 못한 Task는 다른 프로세서에서 Lock이 해제될 때까지 반복적으로 확인하며 대기한다.
                    
                    이 방식은 대기하는 Task의 Context Switching을 발생시키지 않는다는 장점이 있다. 따라서 Critical Section의 내부 명령어 실행 시간이 짧고 Lock의 대기 시간이 짧을 것으로 예상되는 경우, Context Switching에 따른 오버헤드를 줄이기 위해 Spinlock을 사용하는 것이 유리하다.
                    이후에 비교하겠지만, Mutex 같이 연산에서 Context Switching이 많이 일어나는 경우에 만약 CS 실행 시간과 Lock 대기 시간이 짧을 때 Spinlock을 사용하는 것이다.
                    
                    - Study
                        
                        Context Switching은 문맥 교환이라 한다.
                        
                        Task 1의 실행이 중단되고 Task 2가 실행되기 시작할 때, Task 1의 실행 상태(Context)를 PCB 등에 저장한다. 이후 CPU의 실행 상태를 Task 2의 실행 상태로 복원하고 Task 2의 명령을 이어서 실행한다. 나중에 Task 1이 다시 실행되면 PCB에 저장해 두었던 실행 상태(Context)를 복원하여 중단된 지점부터 실행을 재개한다.
                        
            - 뮤텍스 (Mutex)
                - Mutual Exclusion의 약자이다. 이는 Spinlock과 같은 역할을 하며, 소유권을 얻지 못했을때 다른 태스크의 대처에 차이가 존재한다. Spinlock을 기다리는 Task들이 busy waiting을 하고, Mutex는 기다리는 Task들이 Blocked 상태로 Wait Queue에서 대기한다.
                - Spinlock과 마찬가지로 먼저 도착하면 P연산을 통해 자원을 CS에 진입하며, lock을 얻는다. 이후에 도착하는 Task는 자원이 남아있지 않다면 Wait Queue에 들어가 Blocked상태로 대기한다.
                
                뮤텍스에서 lock을 얻는다면, unlock은 lock을 진행한 Task만 가능하며, 이를 소유권 개념이라 한다.
                
                lock을 가지던 Task가 unlock을 했을떄 Wait Queue의 Task를 깨우고, Task는 Ready Queue로 이동하여 스케줄링을 대기한다. 이후 기다리던 Task는 자원을 점유한다.
                즉, 뮤텍스는 2개의 Queue를 활용하는 것이다.
                - Context Switching Cost
                    - 먼저 도착한 Task를 A, 다음으로 도착한 Task를 B라 가정한다.
                        1. B가 lock 시도 → 실패 → B를 대기 큐에 넣음
                        2. **스위칭 ①**: B에서 다른 스레드로 CPU를 넘김
                        3. A가 unlock → B를 깨워 레디 큐로 옮김
                        4. **스위칭 ②**: 스케줄러가 B를 다시 CPU에 올림
                    - 이렇게 뮤텍스는 새 lock을 얻을 때 2번의 문맥 교환 overhead가 발생하므로, CS 실행 시간이 적고, 멀티코어 환경이라면 Spinlock이 유용하다.
            - 세마포어 (Semaphore)
                - 정수 변수 S와, 이를 조작하는 원자적 연산 P, V로 이루어진 동기화 도구이다. 여러 개의 자원을 관리하거나, Task 간 신호를 주고받는 데 사용한다.
                - Mutex와 마찬가지로 자원을 얻지 못한 Task는 CPU를 내려놓고 Blocked 상태로 Wait Queue에서 대기한다.
                - **S, P, V**
                    - S : 현재 점유 가능한 남은 자원의 수. 음수일 경우 |S|는 Wait Queue에서 대기 중인 Task의 수를 의미한다.
                    - P (wait) : S를 1 감소시킨다. S가 음수가 되면 해당 Task는 Wait Queue에 들어가 대기한다.
                    - V (signal) : S를 1 증가시킨다. 증가시킨 S가 0 이하라면 대기 중인 Task가 있다는 뜻이므로, Wait Queue에서 Task 하나를 깨워 Ready Queue로 옮긴다.
                    - P와 V는 원자적(atomic)으로 실행되어야 한다. 그렇지 않으면 S 자체가 경쟁 상태에 빠진다.
                - **종류**
                    1. Counting Semaphore
                        - S의 초기값만큼 여러 Task가 동시에 자원을 사용할 수 있다.
                            1. S = 3
                            2. P → S = 2, 자원 하나 사용 중
                            3. P, P → S = 0, 자원 모두 사용 중
                            4. P → S = -1, 해당 Task는 Wait Queue에서 대기
                            5. V → S = 0, 사용을 마친 Task가 Wait Queue의 Task를 깨워 Ready Queue로 이동시킨다.
                    2. Binary Semaphore
                        - 점유 가능한 자원이 1개로, S의 최대값은 1이다.
                            1. S = 1
                            2. P → S = 0, CS 진입
                            3. P → S = -1, 해당 Task는 Wait Queue에서 대기
                            4. V → S = 0, 대기 중인 Task를 깨움
                        - 하나의 자원만 접근 가능하다면 Mutex와는 어떤 차이점을 가질까?
                - **Binary Semaphore와 Mutex의 차이**
                    - 소유권 : Mutex는 lock을 진행한 Task만 unlock할 수 있지만, Semaphore는 소유자가 없어 어떤 Task든 V를 호출할 수 있다.
                    - 용도 : Mutex는 상호 배제(lock) 전용이고, Binary Semaphore는 주로 Task 간 신호 전달에 사용한다.
                        - 예) ISR에서 V(Give)를 호출하고, Task는 P(Take)로 대기하다가 깨어나 처리한다.
                            - 또한 작업 종료 간의 동기를 맞출 수 있다.
                        - ISR은 Blocked 상태가 될 수 없고 소유자 개념도 없으므로 Mutex를 사용할 수 없다.
                        - 이런 용도 때문에 FreeRTOS의 `xSemaphoreCreateBinary()`는 S = 0(비어 있음)으로 생성된다. 누군가 먼저 V를 해야 P가 통과한다.
                    - 우선순위 상속 : 소유자를 알 수 없는 Semaphore에서는 불가능하고, Mutex에서만 가능하다.
                - **우선순위 역전 (Priority Inversion)**
                    - 우선순위가 H > M > L인 Task 세 개가 있다고 가정한다.
                        1. L이 lock을 얻음
                        2. H가 같은 lock 요청 → L이 unlock할 때까지 대기
                        3. M이 L을 선점함 (M > L)
                        4. H는 lock과 관계없는 M이 끝날 때까지 기다리게 된다. → 높은 우선순위의 H가 M보다 늦게 실행되는, 우선순위가 뒤집힌 상황
                - **우선순위 상속 (Priority Inheritance)**
                    - H가 lock을 기다리는 동안 lock을 가진 L의 우선순위를 H만큼 일시적으로 올려, M이 L을 선점하지 못하게 한다. L이 unlock하면 원래 우선순위로 돌아온다.
                    - lock을 가진 Task가 누구인지 알아야 우선순위를 올릴 수 있으므로, 소유권이 있는 Mutex에서만 가능하다.

        - Answer
            
            Interrupt는 예기치 못한 타밍에 발생하는 이벤트를 직접 CPU에게 알려 처리하는 방식이다. Interrupt 발생 시 IRQ(Interrupt Request)가 발생한다. IRQ의 Pending bit가 1이 되며, 동시에 해당 IRQ가 NVIC로 전달되된다. NVIC의 레지스터에 설정된 우선순위를 통해 실행 IRQ를 정한다. 선점할 IRQ가 정해지면, 해당 IRQ에 대응하는 Handler를 Vector table을 참조하여 찾는다. 이후 Handler 모드로 전환하여 핸들러 실행 등 ISR을 실행한다. 이후 ISR을 마치면 다시 원래 분기로 돌아온다.
            
            Interrupt와 Polling의 차이점은 이벤트를 누가 감지하느냐 이다. Interrupt는 실행 흐름과 무관하게 비동기적으로 갑자기 발생하는 이벤트를 CPU에게 전달하고,Interrupt를 CPU가 직접 처리하는 방식이고, Polling은 CPU, Peripheral이 정해진 주기로 이벤트를 감지한다. Interrupt의 경우 IRQ부터 ISR까지 처리를 위한 overhead가 발생하므로, 잦은 이벤트 발생 시스템과 최대 Polling 주기가 짧은 시스템에서 Polling을 사용한다.
