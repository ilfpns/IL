[[Gst 단계 세분화]]

단계 세분화에 맞춰 gst framework로 개발을 할 것이다.

---

가장 첫 Element인 Camera이다. 요소는 class와 method로 제작한다. 
- CameraElement();  
- ~CameraElement();  
- static bool cameraInit();  
- bool cameraConnect();  
- GstElement *getElement();

총 5개의 메서드로 동작한다. 
다음 두 포인트를 보겠다.

1. v421src
	- Linux의 camera 장치에서 영상을 가져오는 element이다. 리눅스의 V4L2라는 kernel 비디오 장치 인터페이스를 gst에서 사용할 수 있게 해주는 것이다.
	- 이는 리눅스 환경 요소로써, 윈도우 개발 환경에서는 mfvideosrc를 사용한다.
2. link
	- link를 각 elements를 잇는 메서드로써, 가장 첫 단인 camera는 pipeline에 대한 link를 하지 않는다 (pipeline은 전체 bin, elements가 아님)

그 어떤 카메라/코드에서 들어오는 영상을 다음 요소의 src와 이어진 pad로 넣으려면 항상 일정한 규격을 유지해야한다. 그렇기에 camera 안에서 caps를 알아내고, 전처리를 할 것이다.
- Caps : 멀티미디어 데이터 규격 저장 데이터

Camera element안에서 Cap를 처리하므로, caps의 output은 최종 camera의 sink가 되며, 이는 AI 판단 element의 src가 된다.

Gst에서 camera는 프레임워크에 의해서 input으로 전처리된다. 그 후 caps는 * _ many 키워드를 통해 한번에 link한다. 

```
gst_bin_add_many(GST_BIN(pipeline), convert, scale, rate, filter, nullptr);  
addedToBin = true;  
  
if (!gst_element_link_many(input, convert, scale, rate, filter, nullptr)) { }
```
input = camera

Caps에서는 v412src같은 여러 factoryname 키워드를 사용한다. (framework element keywords)
<details> <summary>Framework</summary> 
<br>
Framwork가 게속 헷갈려서 제대로 정리한다. FW는 프로그램의 전체적인 실행 구조와 흐름을 미리 만들고, 개발자가 그 구조에 맞게 필요한 부분을 구현하는 것이다.<br><br>

핵심은 제어권이다. Lib는 개발자가 Lib를 호출하고, FW는 FW가 개발자 코드를 호출한다. <br>즉 전반적인 구조만 정해도 세부 내용을 FW가 처리해주고, Camera같은 element를 input으로 자동으로 처리하는 것이다.<br><br> 이를 제어의 역전 (IoC)라고 한다. 
<br>
<br>
Gst는 개발자가 대략적인 구조만 개발하고 FW가 나머지 부분을 채운다. 그 밖에도 전체적인 실행 구조와 흐름을 Gst가 가진다. 대략적인 흐름에 따라 개발자 코드를 호출하는 방식인 Gst는 FW이다.<br><br>

개발자는 클래스 메서드나, 매크로를 쓸 때 추상화된 모듈을 사용한다. 구현체를 몰라도 된다.

</details>
- convert : videoconvert - 픽셀/포맷 변환
- scale : videoscale - 해상도 변환
- rate : videorate - 프레임레이트 조정
- filter : capsfilter - 원하는 Caps 강제
