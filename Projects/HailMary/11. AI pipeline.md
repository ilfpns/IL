On-Device로 AI를 돌리려면 적어도 3개 파일이 필요하다.
1. 모델 파일 (가중치 + 네트워크 구조)
2. 추론 런타임 라이브러리 (ONNX runtime, TensorRT, etc)
3. 전처리/후처리 코드 (resize, NMS)

---

AI runtime 선택과 그 진행 flow를 정해야한다. 
```
Pytorch Framework learn -> ONNX -> ONNX quantization -> TensorRT (CUDA) ->  Jetson
``` 

TensorRT는 일반적으로 신경망을 실행하기보다, 모델을 Nvidia GPU에서 최대한 효율적으로 실행되도록 분석하고, 컴파일하는 과정이다.

(Yolo를 기준으로) Nividia가 만든 TensorRT는 Pytorch에서 학습한 모델의 OP (연산식)을 하나씩 읽고 다시 쓰는 작업을 처리해야한다. (다른 규격 OP이기 때문에) 그렇기에 TensorRT는 이 OP를 처리하기 좋은 단위로 바꾼다.

이를 Layer Fusion이라고 한다.

TensorRT는 builder를 핵심 키워드라고 할 수 있다.
```
ONNX
 │
 ▼
Network
 │
 ▼
Builder
 │
 ├─ 여러 최적화 방법 탐색
 │
 ├─ Kernel 선택
 │
 ├─ Layer Fusion
 │
 ├─ Precision 선택
 │
 ├─ Memory 계획
 │
 └─ Tensor shape 고려
 │
 ▼
Engine
```
위와 같은 구조일 때 builder가 여러 실행 방법을 고려하여 실제로 사용할 plan을 만든다.
builder는 'optimized execution engine' (실행 설계 계획) 장치라고 할 수 있다. 

ONNX는 서로 다른 Framework의 Op 인터페이스만을 맞추는 것이라면, TensorRT는 이 OP를 gpu에 맞게 최적화 하는 것이다. TensorRT도 별도의 Network를 구성하여 OP를 맞출 수 있는데, 왜 ONNX를 써야할까?

ONNX의 가장 중요한 포인트는 OP interface set이 아닌 IR이라는 것이다. Framework와 Deployment Backend를 분리할 수 있다는 것이다. 

결론적으로
- TensorRT
	- 학습된 Framwork OP를 GPU최적 OP로 최적화 가능 
	- 직접 최적 Plan을 설계
- ONNX
	- IR로 동작하며, 개발, 실행 등의 Framework 다르게 사용 가능
