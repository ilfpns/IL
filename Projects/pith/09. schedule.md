지금 내가 두 개의 Task를 가진다고 하자. Task 1과 2는 제대로 돌아가지 않을 것이다. 
두 task의 실행 스케줄러가 없기 때문이다. 

---
### Round Robin
입력 <-> 출력 <-> 처리를 반복하는 대화형 시스템에서 사용되는 선점 스케줄링 방식이다. 
도착한 프로세스대로 dispatch하고, CPU 자원을 준다. queue로 프로세서를 관리하며, 기아 프로세스가 생기지 않도록 하는 스케줄러이다.

![[Pasted image 20260906192300.png]]
이렇게 프로세서가 들어온가고 가정하자, 시간 할당량이 3이라고 하면, A는 첫 dispatch (queue에서 가져와서 CPU 점유 중)에 일을 절반만 끝내고 queue 맨 뒷 idx로 이동할 것이다.

이 대화형 OS에서 유용하지만 시간 할당량을 잘 선정하는 것에 따라 성능이 상이하다.

RR에서는 systick과 연결되는 time slice를 정해주고, next task를 선정하는 로직을 넣는다.
time slice만큼 task n은 실행되고, next task는 들어온 순서대로 ( = 생성된 순서대로 진행한다)

이제 time slice도 정했고 로직도 짰으면, PendSV를 만들어야 한다.

---

PendSV는 기본적으로 naked하다. 
PendSV는 Cortex에서 제공하는 Exception이다.
가장 중요한 용도로는 Context switching을 해준다. 두 개 이상 Task가 존재할 때 Task1에서 Task2로 CPU 점유를 바꾸며, 두 task 간 문맥 교환이 일어난다.

Systick 안에서 timeslice 시간을 측정할 것이다. 그렇다고 context switching을 systick에서 한다면, Systick의 Exception과 Switching의 Exception이 충돌 문제를 야기할 수 있다. 그렇기에 PendSV로 따로 Exception을 분리한다.

---

대표적으로 PendVS는 
- Exception 대기 (CPU한테 요청)
- context switching Handler 

--- 

왜 PendSV는 naked 해야한다. 

일반 C 함수는 함수 진입 전 준비 작업을 하는데, 이를 function prologue라고 한다. 마찬가지로 함수가 끝나면서 Epilogue가 생긴다.

반면 naked는 이런 프롤로그가 없다. 프롤로그가 있다면 Task, stack을 직접 조작할 때 문제가 생길 수 있기에, 컴파일러가 자동 처리를 하지 않는 naked 키워드를 사용한다.
