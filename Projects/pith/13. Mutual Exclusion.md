Race condition이는 경쟁 상태를 의미한다. 두 개 이상의 task가 하나의 자원에 접근할 때 순서나, 여러 이유로 결론 값이 달라질 수 있는 상태이다. 두 Task는 동시에 자원에 접근하여 위험을 초래할 수 있다.

Crtitical Section은 자원이 있는 곳으로, 동시에 접근되면 안 되는 자원이 있는 코드 영역을 말한다.

Mutual exclusion은 critical section에 하나의 task만 접근 가능하게 하는 것이다. 이는 여러 조건이 있다.
- Progress (진행) : 자원을 사용할 수 있을 때 Task는 유한시간 안에 자원을 점유 해야 하는 상태
- Starvation (기아) : 기다리는 task가 무한정 밀리면서 다른 task는 자원을 접근하지 못하는 상태

이러한 기법들로 자원에 race condition을 보호할 수 있는데, 이는 CPU의 특수 레지스터로도 가능하다
- PRIMASK : 설정 가능한 모든 인터럽트 보류
- BASEPRI : 일정 우선순위 이하 인터럽트 보류
특수 레지스터이므로 CMSIS이다

```c
__disable_irq
~
__enable_irq
```
~는 인터럽트 없이 보호된다

상호배제와 이에 대한 배경에 대해 자세히 알아보자.

---

다중 프로그래밍은 여러 프로세스가 존재한다. 이 프로세스들은 동기화되어 서로 동작을 맞추기도 한다
- 공유 자원 : 여러 프로세스가 접근하는 데이터
- 임계 영역 : 공유 데이터를 접근하는 코드 영역 
- 상호 배제 :  둘 이상의 프로세스가 동시에 임계 영역에 접근하는 것을 막는 것

	앞서 말했듯 상호 배제는 특정 조건을 맞춰야 한다.
- 상호배제 (Mutual exclusion) : 하나의 ps만 cs에 들어갈 수 있어야 함
- 진행 (Progress) : cs가 비었다면 다음으로 진입할 ps를 무한정 미루지 않고 진입시켜야 함
- 한정대기 (Bounded wait) : 특정 ps의 진입 요청 이후에 다른 ps의 진입 횟수가 일정해야한다

여러 방식으로 이런 상호배제 기법들이 구현되었다. 

- 데커 알고리즘
- 다익스트라 알고리즘
- TAS 방식

TAS는 TestAndSet 으로 기계적으로 atomic하게 진행된다, 명령어가 실행되는 도중에 preemption (선점)되지 않게 보장해줌
- 선점 : 현재 실행중인 ps가 일을 마치기 전에 다른 ps로 교체되는 것

CPU의 명령어 수준에서 메모리 값을 읽고 쓰는 동작을 쪼개지 않도록 보장 

하지만 3개 이상의 ps가 실행될 때 2, 3번 ps 중 더 빠르게 다시 lock을 도는 ps가 cs에 들어가게 되고, 운이 안 좋다면 한 ps는 평생 cs로 진입하지 못하고 Bounded wait 문제에 걸린다.

그러므로 진입하지 못한 ps는 아무 일도 하지 않고 계속 loop를 도는 busy-waiting 문제를 발생시킨다. 이러한 문제들을 해결하고자 OS 단위에서 상호 배제를 지원하게 되었다. 

- Spin lock
여기서 사용되는 P, V 연산은 OS가 atomic하게 보장하는 함수이다
- P : 자원 사용
- V : 자원 반납 
두 atomic한 연산으로 구현이 가능한 것 같지만, ps가 두 개 이상이면 오류가 발생한다. 
```
1. ps1이 cs에서 동작하다가 멈춤
2. ps2는 P함수 안에서 while을 돌며 대기 중
3. 중간에 멈춘 ps1은 v를 하지 않음
4. ps2는 계속 loop 중
5. ps1도 atomic한 ps2의 loop를 끊을 수 없음
6. 모든 ps가 접근 불가
   
--------------------------------------------

7. ps2는 ps1이 V를 했든, 하지 않았든 busy waiting중
``` 

spinlock은 계속해서 while을 loop하는 busy waiting 상태를 보이고, task 전체가 block되는 두 단점으로 다른 상호배제 알고리즘인 세마포어와 뮤텍스가 등장한다

먼저 뮤텍스는 value와 guard를 가진다. value는 task가 가지는 일종의 key로 value가 1일 때 자원 선점이 가능하고, 0일 경우에 대기 queue로 들어간다. 

이 경우에 value역시 공유 자원으로 위험한 데이터로 분류된다. 그렇기에 guard라는 mutex 함수 안에서 실행되는 조건문용 변수를 또 하나 두게 된다.

- Semaphore 
임의의 S변수 (세마포어 변수) 하나에 ready queue 하나가 할당된다. 세마포어 종류는 크게 두 가지로 나뉜다.
- Binary semaphore
	- S가 0과 1두 값만 가지는 경우
	- 상호배제 or 동기화의 목적으로 사용
- Counting semaphore 
	- S가 0이상의 정수를 가질 수 있는 경우


P 연산 시 
- cs가 빔 -> 점유
- cs가 사용중 -> ready queue

V 연산 시
- ready queue 확인 -> ps가 대기중 -> 호출
- 자원 반납 

이렇게 queue를 활용해 busy waiting을 해결하고, OS의 지원으로 atomic하게 문제를 해결했다.

지금까지의 방식은 유연하게 사용할 수 있지만, 구현 난이도가 복잡하다 그렇게 발생하는 에러 역시 예측하기 힘든 문제가 있다.
이러한 OS, SW, HW방식 말고 Language level에서 이를 해결할 방법이 있는데 바로 Monitor이다.

- Monitor
Program language layer에서 제시하는 솔루션이다. 언어가 상호배제를 지원하는 방식이다. 


Monitor는 cs와 공유 자원이 동시에 존재하는 공간이다. 
이를 책방으로 예시를 들면, 공유 자원을 책이라는 객체이고, cs는 책을 빌리거나 반납하는 과정을 빗댈 수 있다.

- Entry queue : monitor에 하나씩 있는 진입 queue이다
- Mutual Exclusion : 항상 하나의 ps만 접근 가능
- Condition queue : 특정 조건을 기다리는 ps 대기 큐이다
- Signaler queue : 다음 큐안에 ps를 call 하기 위해 존재하는 큐

이번에도 책방을 예로 상황을 설명하겠다.

func은 총 2개이다. 대출/반납
```
1. 대출에 첫 ps1이 entry queue로 들어오고 자원을 가진다.
2. ps2는 책이 다시 반납될 때까지 기다려야한다. 
3. ps2는 condition queue로 이동해 조건을 기다린다.
4. ps1는 책을 반납하고 entry queue로 들어온다
5. ps1은  signaler queue로 이동하여 condition queue에 시그러늘을 보낸다.
6. ps2는 책을 가져가고 ps1은 signaler queue에서 나오고 이후 일을 처리한다.
```
